# АРМ-112 · учебный симулятор ДДС

Локальный тренажёр: карточки происшествий, автомат статусов, два серверных таймера, проверка адресов и грамотности, телефония, оценка и пульт преподавателя. Шрифты, звуки и справочники поставляются локально; GPU не требуется.

Приватный репозиторий: [DestYchen/dispatcher112-trainer](https://github.com/DestYchen/dispatcher112-trainer). [Состав публикации и работа с Git](docs/GITHUB.md).

Состояние приёмки: [PROGRESS.md](PROGRESS.md). Задание: [README-SPEC.md](README-SPEC.md). Решения по неоднозначностям: [docs/DECISIONS.md](docs/DECISIONS.md).

**Чтобы показать программу:** включите Docker Desktop и дважды нажмите **[Show.cmd](Show.cmd)**. Откроются два независимых окна с заполненными данными входа: преподаватель и обучающийся. Два упражнения уже подготовлены, таймеры начнутся по команде преподавателя. [Сценарий показа на 5–7 минут](docs/SHOWCASE.md).

Анализ нового ТЗ и примеров из папки «данные UI»: [соответствие требованиям заказчика](docs/CUSTOMER-SPEC-REVIEW.md). Работают оба вида упражнений, текстовые/голосовые обращения, черновики, оценка, SIP с гарнитурой и записями. Добавлены группы, назначенные материалы и модули, история с обратной связью, критерии успешности, локальная генерация и отдельный нейросетевой прогноз. Реализованы техническое обслуживание, автоматический монитор, резервирование/восстановление, подписанные обновления, несколько backend, Excel/CSV/XML/PDF, MP3/WAV и локальный комплект поставки. Результаты приёмки и внешние остатки — целевой аппаратный стенд и отсутствующие оригиналы — перечислены в PROGRESS.md.

Для **уже установленного** проекта с запущенным Docker Desktop достаточно команд ниже; GNU Make не нужен. Запускайте из папки проекта с активной `.venv`:

```powershell
python scripts/compose.py up --detach --no-build --wait
```

Откройте **https://localhost:5173**. Остановка с сохранением базы и файлов: `python scripts/compose.py down`. Монитор сервисов запускается и останавливается вместе с проектом; состояние — `python scripts/service_monitor.py status`.

Для заполнения карточек создайте занятие с видом упражнения «Приём обращения и заполнение карточки», назначьте утверждённые сценарии и начните занятие. Обучающийся открывает входящее обращение, заполняет поля, сохраняет черновик и сдаёт карточку. После сдачи доступен разбор; в пульте преподавателя — «Подготовить сценарий из этой карточки». Проверьте его в библиотеке подготовки, подтвердите и назначьте на занятие с действиями ДДС. В смешанном занятии пакетная выдача чередует оба вида упражнений.

## Требования и запуск

Docker Engine с Compose v2; на Windows — Docker Desktop с WSL2. GNU Make и Python 3.11+. По полному ТЗ сервер: от 6 ядер CPU, 32 ГБ ОЗУ и NVMe 512 ГБ; рабочее место: Core i5, 16 ГБ ОЗУ, SSD 256 ГБ, гарнитура и гигабитная локальная сеть. Сборка требует доступа к реестрам образов и пакетов; работа приложения — только внутри локального контура.

```sh
python -m pip install -r scripts/requirements-tls.txt
python scripts/bootstrap.py
python scripts/prepare_tls.py --activate
make demo
```

Команда заранее подготавливает локальную модель Qwen2.5:3b (около 1,9 ГБ весов плюс образ Ollama), собирает и запускает сервисы, применяет Alembic, загружает справочники и готовит занятие с тремя обучающимися, рабочими местами и девятью карточками. Подготовленная модель проверяется по SHA-256 и повторно не скачивается. Повторный запуск сохраняет пароли и готовое/идущее занятие. Таймеры начинаются после кнопки «Начать занятие» у преподавателя.

Откройте [рабочее место](https://localhost:5173). API: [проверка сервера](https://localhost:8000/healthz), [метрики](https://localhost:8000/metrics). Для доверия браузера администратор клиентского места устанавливает публичный `.secrets/pki/ca.crt`; закрытые ключи на клиент не переносятся. Подробности и подключение по локальной сети: [TLS.md](docs/TLS.md). `--activate` сохраняет выбор TLS в `.env`, поэтому следующие `make up`, `make check` и `make down` используют ту же конфигурацию. В ответах API есть `X-Request-ID`.

| Роль | Логин | Пароль |
| --- | --- | --- |
| Администратор | `admin` | `admin` |
| Преподаватель | `teacher` | `teacher` |
| Обучающиеся | `student1`, `student2`, `student3` | `student` |
| Преподаватель показа | `demo.teacher` | `Showcase112!` |
| Обучающийся показа | `demo.student` | `Showcase112!` |

Адрес: https://localhost:5173 на сервере. Для открытия с других компьютеров класса (локальная сеть или Tailscale) задайте в `.env` `APP_BIND=<адрес сервера>`, `VITE_ALLOWED_HOSTS=<имя сервера>` и `TLS_CORS_ORIGINS` с этими адресами (пример в `.env.example`), затем `python scripts/compose.py up --detach --no-build --wait`. Сертификат учебного стенда самоподписанный: примите предупреждение браузера или установите `.secrets/pki/ca.crt`.

Это открытые учебные учётные записи. В рабочем классе администратор создаёт собственные аккаунты и блокирует ненужные демонстрационные. Пароль БД и JWT-секрет `make bootstrap` создаёт случайно в локальном `.env`, не выводя значения. Существующий `.env` сохраняется.

Для запуска без демонстрационного занятия:

```sh
make models
make up
make migrate
make seed
```

На Windows запускайте команды в PowerShell. Если GNU Make не находится, добавьте каталог с `make.exe` в PATH или вызывайте его полным путём. Node.js и PostgreSQL на основной машине не требуются.

На текущем компьютере хранилище Docker перенесено в `D:\DockerData\wsl`; папка проекта и команды запуска остались прежними. Пути резервной копии и результаты проверки: [перенос Docker на D:](docs/DOCKER-STORAGE.md).

Полную резервную копию можно развернуть как отдельную работающую установку с кодом, настройками и данными через `scripts/recover_snapshot.py`. Она проверяется в обслуживании и открывается отдельной активацией; исходный экземпляр сохраняется. Команды, необходимые образы и ограничения: [восстановление](docs/RECOVERY.md).

## Расширенная демонстрация: три рабочих места

Для первого показа вдвоём используйте [Show.cmd и короткую инструкцию](docs/SHOWCASE.md). Ниже — отдельный сценарий занятия с тремя обучающимися из `make demo`.

1. В отдельном окне войдите как `teacher`, найдите «Демонстрация АРМ-112: три рабочих места», откройте пульт и начните занятие.
2. В трёх независимых профилях/контекстах браузера войдите как `student1`–`student3`. Обычные вкладки одного профиля разделяют cookie и не подходят для разных пользователей.
3. Откройте карточку, прочитайте описание, пройдите «Принята → Реагирование начато → Прибыли → Работы ведутся → Работы завершены». Первичный срок — 30 с, обработка — 180 с.
4. В карточке с докладом нажмите Alt+T, наберите 2201, введите адрес, вид происшествия и сведения о пострадавших; завершите доклад, затем карточку. Вызовы идут только в симулятор.
5. На пульте посмотрите действия и оценки, завершите занятие, откройте отчёт. Строка участника открывает разбор и корректировку с обоснованием; PDF содержит семь заданных колонок.

Alt+1/Alt+2 выбирают первичный статус, Alt+C переводит фокус в комментарий, Esc закрывает панель/диалог, `?` показывает памятку. При разрыве связи таймеры продолжаются, действия сохраняются на рабочем месте и отправляются с прежним ключом идемпотентности.

Интерфейс перестраивается для окон от 360 px. На телефоне переходите между очередью, карточкой и действиями по закреплённой панели; широкие таблицы прокручиваются внутри своего блока. Создание занятия у преподавателя раскрывается по «Новое занятие». Браузерная проверка адаптивности: `python scripts/check_responsive.py` (требуются Playwright/Chromium и запущенное демо).

## Проверки и обслуживание

```sh
make check           # Ruff, mypy --strict, pytest, ESLint, TypeScript, Vitest, сборка
make test            # тесты с настоящими PostgreSQL, Redis и LanguageTool
make fmt             # форматирование
make backup          # немедленная резервная копия
make verify-backup   # полный снимок и восстановление в отдельную проверочную БД
make load            # 20 настоящих сессий по 10 карточек, HTTP + WebSocket
make down            # остановка, данные сохраняются
```

Для браузерных и нагрузочных скриптов на основной машине установите `scripts/requirements-acceptance.txt` и Chromium командой `python -m playwright install chromium` на этапе подготовки. Доступ во внешнюю сеть во время приёмки не нужен. Артефакты записываются в `artifacts/`; `make check` использует отдельную БД `dispatcher_test` и Redis DB 15.

`make load` выполняет 200 полных карточек с паузой в среднем две секунды между действиями, с включёнными оценкой, адресами, LanguageTool, аудитом и пультом. Проверяются все 1400 событий, изоляция студентов и сохранённые оценки. Для проверки предельной нагрузки без пауз запустите `python scripts/check_load.py --think-time 0` после подготовки новой нагрузки. На текущем компьютере для класса 20 участников используются два backend, для профиля 100 — четыре: [настройка и результаты](docs/CLUSTER.md). Один процесс предназначен для небольшой демонстрации. Тестовые учётки после завершения деактивируются, история остаётся. Отдельный benchmark записи: `python scripts/compose.py run --rm checks python -m tests.check_database_write` (500 отдельных транзакций в тестовой БД после `make check`).

Администратор управляет пользователями, рабочими местами, импортом XLSX/CSV, журналом и диагностикой. По умолчанию резервное копирование выполняется ежедневно в 03:00 по Москве, закрытый каталог `.backups/`, 14 успешных копий. Приложение получает из `data/backup-status/` только сведения о копиях и результатах проверок; содержимое архивов ему не монтируется. Журнал аудита не редактируется и не удаляется; его история входит в резервные копии. API и workers используют ограниченную роль `dispatcher_app`, backup — `dispatcher_backup` с чтением рабочих таблиц и созданием собственных проверочных БД, без SUPERUSER/CREATEROLE. Миграции и выдачу прав выполняет отдельный одноразовый сервис `migrate`, тестовую БД подготавливает сервис `checks`. Секрет `BACKUP_DB_PASSWORD` создаётся при bootstrap; границы доступа и порядок обновления — [DEPLOY.md](docs/DEPLOY.md).

Все 13 постоянных сервисов имеют корневую файловую систему только для чтения, запрет повышения привилегий и нулевые capabilities у основных процессов. Прикладные и вспомогательные процессы работают без root; backup сохраняет UID 0 для чтения исходных закрытых ключей, с записью только в архивы и служебные каталоги. Одноразовый `prepare_runtime` без сети подготавливает права и частные копии сертификатов. Frontend-проверки выполняются отдельным `frontend_checks` без сети. Проверка действующих процессов: `python scripts/check_runtime_permissions.py`; границы доступа и установочные исключения — [DEPLOY.md](docs/DEPLOY.md).

В разделе администратора **«Резервные копии»** доступны список копий, расписание, создание полной копии и проверка восстановления. Завершите занятия, включите обслуживание с причиной и выберите действие. После завершения отключите обслуживание. Проверка восстанавливает файлы и БД отдельно и сохраняет рабочие данные. Задание продолжается после закрытия вкладки, результат и аудит сохраняются сервером. Проверены переключение основного адреса на восстановленный экземпляр, повтор команды и возврат с сохранением обеих БД: [порядок действий](docs/RECOVERY-SWITCH.md). Сервис backup работает самостоятельно; запуск технического контроллера для этих действий не требуется.

Новые копии сохраняют также исходники API/UI, миграции, локальные ресурсы, документацию и файлы сборки/зависимостей. Старые копии остаются доступными и помечаются как копии без исходников. Образы Docker и установочные пакеты нужны отдельно; точный состав — [RECOVERY.md](docs/RECOVERY.md).

Подписанные пакеты ПО: раздел администратора «Обновления программы» проверяет подпись загруженного ZIP, показывает историю и готовит подписанный запрос оператору сервера. Локальная команда `install_update.py execute-request` выполняет установку с обслуживанием, полным снимком, миграциями и откатом до активации; отдельный запрос активирует проверенную версию — [UPDATES.md](docs/UPDATES.md). Обычный запуск через `make` использует закреплённую конфигурацию установленного выпуска. Открытый ключ издателя заранее настраивается на сервере; веб-приложение не получает Docker socket. Результаты сквозной приёмки этого процесса и технического обслуживания перечислены в [PROGRESS.md](PROGRESS.md).

**«Технический отчёт»** показывает агрегированное использование за выбранный период, серверные ошибки, неудачные операции/генерацию/звонки и проверки защиты БД. Доступен полный JSON-экспорт периода. Ошибки API 5xx сохраняются в неизменяемом аудите без тела запроса и учебных данных; сохраняются после перезапуска. Текущие HTTP-счётчики имеют отдельную дату начала процесса. Отчёт не требует Docker socket; состав и ограничения проверок — [DIAGNOSTICS.md](docs/DIAGNOSTICS.md).

## Состав поставки и ограничения

Классификатор содержит 24 группы, 1200 типов, 58 служб; справочник — 50 московских улиц. Это авторские учебные данные, не нормативный оригинал заказчика: [data/README.md](data/README.md). Исходные PDF-билеты не предоставлены; OCR проверен на явно синтетическом наборе 90 билетов. Команда импорта: `docker compose run --rm backend python -m app.seeds.import_tickets /data/имя.pdf`.

Сценарии по умолчанию генерируются локальными шаблонами, затем утверждаются преподавателем. Для установленной локальной Ollama предусмотрен `GENERATION_BACKEND=local_llm`; внешние адреса генерации запрещены. В занятии LLM не вызывается.

Четыре голоса уже записаны в WAV. Модель Silero для работы не нужна; происхождение и лицензия — [data/voices/README.md](data/voices/README.md). Доклад вводится текстом; опциональный STT в этой поставке не реализован, `STT_ENABLED=false`.

Для IP-телефонии нажмите «Включить гарнитуру», разрешите микрофон и проверьте звук. Входящие голосовые упражнения выбираются при создании занятия. Подробности, записи разговоров и приёмка 20 клиентов: [docs/TELEPHONY.md](docs/TELEPHONY.md). По умолчанию запуск предназначен для localhost; доступ с других компьютеров требует настройки HTTPS/WSS и локального адреса медиасервера.

Документы: [архитектура](docs/ARCHITECTURE.md), [изолированный контур](docs/DEPLOY.md), [зависимости и лицензии](docs/LIBRARIES.md).

Эксплуатационные настройки доступны администратору в «Параметры системы»: пулы и тайм-ауты БД, сроки SIP-вызовов и журналирование. Изменения выполняются в обслуживании с аудитом и подтверждением всех процессов — [инструкция](docs/RUNTIME-CONFIGURATION.md).

Проверка рабочих файлов доступна в «Техническом отчёте» и «Резервных копиях». Администратор явно выбирает проверенную полную копию как эталон; текущие файлы сравниваются автоматически и по запросу. Состав проверки и ограничения — [FILE-INTEGRITY.md](docs/FILE-INTEGRITY.md).
