# Несколько серверных процессов

Реализованы общая доставка событий через Redis Stream, присутствие учеников между процессами, блокировка конкурентных тиков планировщика и локальная команда изменения числа backend. 27.09.2026 проверены 100 участников на четырёх backend и остановка одного из двух backend. Это процессы одного Docker-хоста; отказ отдельного физического компьютера этим испытанием не проверяется.

В режиме обслуживания, из корня проекта, с UUID активного администратора:

```powershell
python scripts/scale_backends.py --replicas 2 --actor UUID
```

Число процессов сохраняется для `make up`, восстановления и пакетного обновления. Допускается 1–4, при этом сумма пулов и переполнения всех backend, worker и SIP должна помещаться в бюджет PostgreSQL с резервом. При необходимости сначала уменьшите размеры пулов через UI. В «Параметрах системы» видны подтверждения каждого процесса. После их появления снимите обслуживание. Для возврата к одному процессу повторите команду с `--replicas 1`.

Подтверждение проверяет именно заданное число backend: один оставшийся процесс не выдаётся за два применивших настройки. Повтор прерванной команды после уже завершённой серверной транзакции восстанавливает локальный журнал без повторного применения. Повреждённое уведомление в общей очереди фиксируется в системном журнале и не задерживает следующие события.

Для четырёх backend использованы пул API 18 и overflow 0: вместе с worker и SIP бюджет составляет 82 соединения при доступных 87. Сначала в обслуживании примените размеры пулов в «Параметрах системы», затем измените число процессов и дождитесь подтверждений всех четырёх. При возврате уменьшите число процессов до одного, дождитесь исчезновения старых подтверждений, верните обычный пул API 20 / overflow 5 и снимите обслуживание. Для трёх демонстрационных участников достаточно одного процесса. Для класса из 20 участников на текущем компьютере оставлены два backend с пулом API 20 / overflow 5: общий бюджет 70 при доступных 87; обслуживание выключено.

NGINX разрешает адреса backend через локальный Docker DNS; API и WebSocket направляются в общий upstream. Подключение ограничено двумя секундами, повтор допустимого запроса — тремя попытками в пределах трёх секунд. NGINX не повторяет уже отправленные неидемпотентные запросы. Срок неактивного upstream keep-alive — 15 секунд, у backend — 30. При отключении процесса браузер переподключается и загружает актуальное состояние из БД, сохраняя локальную очередь с ключами повторных операций. Присутствие с другого процесса имеет срок 15 секунд; несколько вкладок учитываются независимо.

Планировщик удерживает короткую Redis-аренду на 950 мс: общий пульт вычисляется одним процессом за тик. Запись дополнительно сериализуется блокировкой PostgreSQL, транзакция завершается до чтения пульта. Пакет уведомлений отправляется через Redis pipeline с сохранением порядка. После аварии аренда истекает и работу продолжает другой процесс.

## Измеренные результаты

- 100 участников × 2 карточки, четыре backend: p95 HTTP 677,3 мс, все 1400 событий доставлены, максимальная задержка события 797 мс. Открытие карточки в пяти одновременно работающих браузерных профилях: 454–591 мс; отчёт JSON — 87 мс. Действия распределены по времени: пауза 3,75–6,25 с, средняя 5 с. Это 100 HTTP/WS-сессий и пять настоящих браузеров, а не 100 физических рабочих мест. Артефакт: `artifacts/ui-review/full-tz-load-100-6.json`.
- Остановка одного из двух backend: пять WebSocket на остановленном процессе закрылись, пять на оставшемся продолжили работать. Запрос после отказа занял 34,38 мс; повтор действия не создал дубль и не изменил сроки. Процесс восстановлен. Артефакт: `artifacts/ui-review/full-tz-failover.json`.
- Более жёсткие нагрузочные профили и прогоны с конкурирующим браузерным/API-драйвером не прошли пороги; их результаты сохранены. Указанные цифры относятся только к описанному профилю.

Машина проверки: Core i5-12450H, физическая ОЗУ 15,73 ГБ, Docker — 7,62 ГБ. Требуемый ТЗ сервер с 32 ГБ ОЗУ и 100 отдельных рабочих мест недоступен; результат не подменяет его приёмку.

События приложения сохраняются в ограниченном Redis Stream (около 10 000 последних). Каждый backend читает его независимо, продолжая с последней позиции после временного разрыва связи. Сообщения существующих SIP/генераторов сохраняют собственный канал. БД остаётся источником истины: это не гарантия бессрочного хранения уведомлений и не кластер высокой доступности PostgreSQL/Redis. При отказе всего компьютера применяется восстановление из копии.

В текущем исполнении несколько процессов запускаются на одном Docker-хосте. Развёртывание по разным физическим узлам, отказ общего хранилища и аппаратная матрица остаются отдельными невыполненными критериями полного ТЗ.

Заключительный профиль 20×10 на одном backend дал p95 332,37 мс и не прошёл порог 300 мс; потерь событий нет. Этот результат сохранён как full-tz-load-20-final.json. Для класса применяется конфигурация двух backend; повторный замер на двух процессах прошёл: p95 164,46 мс, все 1400 событий доставлены, максимальная задержка 351 мс, JSON-отчёт 152 мс. Паузы 1,5–2,5 с; результат — full-tz-load-20-two.json.
