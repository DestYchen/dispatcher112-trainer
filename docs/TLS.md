# Защищённое развёртывание

Стенд переключён на `docker-compose.tls.yml` 26.09.2026. Фактически проверены HTTPS/WSS, TLS PostgreSQL/Redis, запрет незашифрованных межсервисных соединений и полный браузерный SIP-звонок. Приёмка этапа 15 завершена: результаты в PROGRESS.md. Постоянный контроллер с Docker socket не требуется: подписанные операции выполняет локальная команда оператора, монитор только читает состояние.

## Сертификаты

`scripts/prepare_tls.py` создаёт отдельный локальный центр сертификации и ключ для каждого сервиса. Закрытый ключ центра находится в `.secrets/pki/private/ca.key`; обычные сервисы получают только собственный каталог сертификатов. В Git, образы и общую папку `/data` ключи не включаются. Центр действует десять лет, сервисные сертификаты — год; повторный запуск сохраняет действующие ключи и обновляет сертификат за 30 дней до окончания или при добавлении имени узла. Центр не заменяется автоматически.

Для backend, worker, sip_worker, telephony, frontend, gateway и двух TLS-прокси LanguageTool/Ollama одноразовый `prepare_runtime` копирует только соответствующие CA/сертификат/ключ в восемь томов `runtime_*`, с владельцем 10001 и правами 0600. Исходные ключи в `.secrets` не меняют владельца или прав; закрытый ключ CA в рабочие тома не попадает. Тома подключены только для чтения: `/run/tls`, у Asterisk — `/run/credentials/tls`. Основные процессы LanguageTool/Ollama не получают ключи своих прокси. Установочный процесс работает без сети и Docker socket. После обновления сертификатов выполните `docker compose run --rm --no-deps prepare_runtime`, затем перезапустите использующие их сервисы; обычный `docker compose up` также выполняет подготовку перед запуском зависимых сервисов.

На установочной машине подготовьте Python-зависимость из `scripts/requirements-tls.txt`, затем выполните:

```powershell
python scripts/bootstrap.py
python scripts/prepare_tls.py --activate
# Для класса: повторите с --host ИМЯ_СЕРВЕРА или --host IP_СЕРВЕРА
docker compose -f docker-compose.yml -f docker-compose.tls.yml up --build --detach --wait --wait-timeout 240
```

Установочная зависимость зафиксирована на cryptography 50.0.1 по [официальному журналу выпусков](https://cryptography.io/en/latest/changelog/); 13 установочных тестов прошли с этой версией. Для изолированной установки wheel и его зависимости нужно подготовить заранее. В рантайме генератор сертификатов и внешний сервер сертификатов не используются. `--activate` сохраняет обе Compose-конфигурации и явный разделитель путей в `.env`; последующие обычные команды Compose сохраняют TLS.

Сертификаты содержат SKI/AKI и KeyUsage и проходят `VERIFY_X509_STRICT`, включённый по умолчанию в [Python начиная с 3.13](https://docs.python.org/3/library/ssl.html#ssl.create_default_context). Для старого CA, выпущенного промежуточной версией установщика без идентификаторов, предусмотрен явный `--repair-ca-extensions`: он сохраняет закрытый ключ, субъект и срок, перевыпуская публичный сертификат; прежний публичный сертификат остаётся в `ca-before-extensions.crt`. После этого обновите публичный CA на клиентских местах и перезапустите сервисы. Обычный запуск такой CA молча не меняет. На этом стенде исправление уже применено, системное хранилище доверия не изменялось.

Для доверия браузера администратор клиента устанавливает **только публичный** `.secrets/pki/ca.crt` в доверенные центры либо выпускает сервисные сертификаты от инфраструктуры организации. Скрипт не меняет доверие Windows/Linux. Не устанавливайте закрытый ключ CA на клиентские места. Для доступа по сети настройте опубликованные адреса в Compose, `SIP_MEDIA_ADDRESS` и список `TLS_CORS_ORIGINS` в `.env`; имена должны входить в SAN сертификата. По умолчанию порты привязаны к localhost.

## Каналы

| Соединение | Подготовленная защита |
| --- | --- |
| Браузер → шлюз | HTTPS/WSS, порты 5173/8000, Secure session-cookie |
| Шлюз → UI/API | HTTPS с проверкой CA и имени frontend/backend |
| API/worker → PostgreSQL | TLS, verify-full; сетевые соединения без TLS отклоняются pg_hba |
| API/worker → Redis | TLS, проверка имени/CA, пароль; обычный TCP-порт отключён |
| API → LanguageTool/Ollama | HTTPS; отдельный TLS-прокси в сетевом пространстве соответствующего сервиса |
| API/SIP-worker → Asterisk | HTTPS/WSS на 8089 |
| Браузер ↔ Asterisk, звук | DTLS-SRTP, реализовано и измерено на этапе 13 |
| API → технический контроллер | HTTPS плюс отдельный токен; профиль выключен до разрешения запуска |
| Резервирование → PostgreSQL | TLS, verify-full |

LanguageTool и Ollama принимают HTTP только на loopback собственного сетевого пространства, где находится их TLS-прокси. Незашифрованные обращения между контейнерами не предусмотрены. Для LanguageTool привязка к localhost без `--public` подтверждена [исходным кодом версии 6.6](https://github.com/languagetool-org/languagetool/blob/v6.6/languagetool-server/src/main/java/org/languagetool/server/HTTPServer.java). Локальные Unix sockets, файлы, Docker DNS и loopback пары «сервис–прокси» не заявляются как TLS-соединения.

## Что проверено и что осталось

Тринадцать тестов `scripts/test_tls.py` выполняют настоящий TLS handshake с `VERIFY_X509_STRICT` через MemoryBIO для всех 12 сертификатов, проверяют соответствие сертификатов монтированиям Compose, недоверенный CA, чужое имя, повторную подготовку, отказ замены неполного CA, явное исправление старого CA с сохранением ключа и сохранность настроек при активации. Четыре backend-теста проверяют параметры Redis/arq, локальный HTTPS-адрес модели и отказ при отсутствующем CA.

Реальный прогон `tests.check_tls_runtime` подтвердил TLS 1.3 для UI/API/шлюза/LanguageTool/Ollama и PostgreSQL, HTTPS ARI, Secure-cookie, защищённый WebSocket, отказ обычного HTTP для шести сервисов, отказ PostgreSQL без TLS и Redis без TLS/пароля. Результат: `artifacts/ui-review/tls-acceptance.json`. Браузер прошёл исходящий SIP-звонок, запись и единственный доклад, все пять переходов карточки и семь ширин 360–1920 px (`sip-tls-browser.log`, `sip-outgoing.json`). В изолированном профиле Chromium закреплён публичный ключ сертификата шлюза; HTTP-клиент Playwright проверяет локальный CA и имя. Системное хранилище доверия не менялось.

Разделение ролей БД применено: API/worker используют `dispatcher_app` без SUPERUSER/CREATEDB/CREATEROLE и изменения аудита. 11 тестов проверяют данные, DDL, триггеры, системные пароли и ACL аудита; отдельный реальный прогон подтвердил эту роль у работающего API. После ограничения всех 13 процессов повторены реальная TLS-проверка и SIP-звонок с записью (`auxiliary-tls-runtime.log`, `auxiliary-sip-browser.log`); исходные CA и сертификаты сохранены. Права процессов проверяет `scripts/check_runtime_permissions.py`, установочные исключения описаны в DEPLOY.md. Проверены восстановление полного снимка, переключение основного адреса, повтор и возврат с неизменностью прежнего аудита. Результат — full-tz-recovery.json, порядок — RECOVERY-SWITCH.md.

Backup подключается по тому же проверяемому TLS от `dispatcher_backup` с отдельным `BACKUP_DB_PASSWORD`: SELECT рабочей схемы и CREATEDB для восстановления в свою временную БД, без SUPERUSER/CREATEROLE. 20 тестов проверяют ограничения, восстановительную БД и повторную выдачу прав. Реальный UI создал и восстановил 218 файлов, 512 пользователей, 1200 типов и 28 641 запись аудита с защитным триггером; результат содержит `database_role=dispatcher_backup` (`backup-role-live.log`, `backup-live.json`). Рабочая БД сохранена, временная удалена. Файловый доступ доверенного backup к полной конфигурации описан в DEPLOY.md и не считается устранённым SQL-ограничениями.
