# Переключение основного адреса

27.09.2026 принято реальное переключение основного адреса на восстановленную установку, повтор без повторного исполнения, возврат и его повтор. Проверены неизменность 28 822 исходных записей аудита восстановленной БД и 28 876 исходных записей основной БД, а также учебных данных. Прерванный возврат возобновлён из сохранённого состояния. Результат: `artifacts/ui-review/full-tz-recovery.json`.

Нужны две работающие БД и backend с текущим модулем переключения, одинаковый активный ADMIN из снимка, завершённые занятия/генерация/звонки. Полная недоступность исходной БД не позволяет извлечь аудит после последней копии: в этом случае сначала восстановите её доступность либо используйте отдельный адрес восстановленного экземпляра. Исходные тома никогда не удаляются.

Из **корня исходной установки**, с UUID администратора из пульта:

```powershell
python scripts/switch_recovery.py promote --target .recovery/restored --actor UUID --reason "Переход на восстановленную установку"
python scripts/switch_recovery.py status --target .recovery/restored
python scripts/switch_recovery.py rollback --target .recovery/restored
```

Сначала программа блокирует новые изменения в обеих системах и закрывает их шлюзы. Подписанные архивы аудита сохраняются в каталоге восстановления. Совпадающие записи пропускаются; записи отсутствующей ветки добавляются как `RECOVERY_AUDIT_IMPORTED` с исходным проектом, ID, SHA-256 и полным исходным событием. Исходные строки не изменяются, конфликты числовых ID не затирают события. Повторный импорт не создаёт копии одного события.

Затем порты исходного шлюза передаются восстановленному. Его ключ сессий отличается — пользователи входят повторно. После возврата аудит новой ветки переносится в исходную БД, а обе системы возвращаются на прежние адреса. Учебные записи двух БД автоматически не объединяются: новые занятия восстановленного экземпляра остаются в нём. Для продолжения этих занятий сохраняйте восстановленный экземпляр основным.

Порты и CORS сохраняются отдельно от выпуска, применяются через `scripts/compose.py` / `make up` и входят в полную копию. Нужен Docker Compose с поддержкой `!override` (локальная версия 2.35.1). Допускаются только локальные HTTPS-адреса и loopback-порты, как в имеющемся установщике восстановления.

При прерывании состояние и архивы сохраняются. Повтор команды продолжает операцию; `rollback` возвращает исходные адреса после восстановления доступности обеих БД. Ограничение одного переноса: 100 000 событий и 64 МиБ исходных данных аудита; при превышении процедура останавливается, сохраняя БД. `make up` не снимает блокировку незавершённого переключения.

После RETURNED новая команда `promote` с администратором и причиной начинает следующий цикл. Завершённая подписанная запись и архивы предыдущего цикла сохраняются в `switch-UUID/`. При переносе адреса пересоздаются backend и шлюз; фоновые процессы не используют CORS и не требуют перезапуска для этой операции.
