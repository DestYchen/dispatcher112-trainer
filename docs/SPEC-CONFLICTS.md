# Вопрос по нормативным правилам адресов

Исходные документы не изменены. Пользователь поручил разрешать сомнения самостоятельно: принято контекстное правило ниже, решение зафиксировано в DECISIONS.md. Блокировки продолжения нет.

## Точное совпадение и подмена существующей улицы

- SPEC.md §3.2 требует включить в streets обе улицы: Дубнинская и Дубининская.
- SPEC.md §6.3: «точное совпадение со streets.name_norm → ок»; trigram-поиск выполняется только иначе.
- PLAN.md, этап 6: «„Дубининская“ вместо „Дубнинская“ → ADDRESS_TYPO», в suggestions должен быть верный вариант.

При буквальном применении §6.3 обе строки проходят точную сверку и не получают ADDRESS_TYPO. Для критерия этапа 6 нужно отдельное правило: учитывать эталонный адрес карточки и распознавать подмену одной существующей улицы другой. Оно требует уточнить безусловное «точное совпадение → ок».

Предложение: сначала проверить контекстное соответствие эталонному адресу для пар-ловушек; затем выполнять обычную сверку справочника. Существующая улица без конфликта с адресом карточки не должна получать ложное сообщение «такой улицы нет».

## Нормализация для trigram-критерия

На PostgreSQL 15 получены реальные результаты:

```sql
SELECT similarity('дубининская', 'дубнинская');
-- 0.64285713
SELECT similarity('дубининская улица', 'дубнинская улица');
-- 0.75
```

Таким образом, сформулированный в этапе 1 порог > 0.7 выполняется для полных названий с родовым словом «улица», но не для голых названий. Первоначальное сообщение о безусловной невозможности этого численного критерия было уточнено после второго измерения.

Предложение: сохранить порог > 0.7, явно нормализовать запросы и справочник к полным названиям; отдельно покрыть подмену известной улицы контекстным правилом. Не подменять PostgreSQL similarity иной метрикой.
