# Локальные пакеты программы

Реализованы сборка, проверка цифровой подписи, подготовка пакета и локальный установщик с обслуживанием, полным снимком, миграциями, активацией и откатом до активации. Административный UI проверяет пакеты, готовит подписанные запросы локальному оператору и показывает историю. Весь этап 15 этим механизмом не закрывается. Команда `software_package.py prepare` проверяет файлы и зависимости; программу обновляет отдельная команда `install_update.py apply`.

## Формат и доверие

`dispatcher-update-1` — ZIP без сжатия: `release.json` и файлы под `program/`. Описание содержит версию, время выпуска с часовым поясом, описание изменений, точные SHA-256 ID образов всех 17 компонентов развёртывания и размер/SHA-256 каждого файла. Подпись Ed25519 проверяется открытым ключом издателя, который администратор получает по отдельному доверенному каналу. Ключ внутри архива не принимается как источник доверия. Реализация использует [API Ed25519 библиотеки cryptography](https://cryptography.io/en/latest/hazmat/primitives/asymmetric/ed25519/).

Пакет включает API/UI, миграции, локальные ресурсы интерфейса, тесты, документацию, скрипты, lock-файлы, Dockerfile, оба файла Compose и шаблоны `infra`. Рабочие `.env`, `.secrets`, база данных, пользовательские файлы и модели в `data`, архивы `.backups` в него не входят. Секретные файлы, ссылки, неподдерживаемые пути, совпадения имён без учёта регистра, лишние/повторные ZIP-записи, изменённые размеры/хеши и неподписанные файлы отвергаются. Предел: 10 000 файлов, 256 МиБ данных, 2 МиБ описания. Подпись подтверждает издателя и целостность, но сама по себе не доказывает совместимость новой версии с данными.

Архив не содержит Docker-образы. Их доставляют отдельно в офлайн-комплекте и заранее загружают локально; проверка не скачивает образы. Компонент `control` с постоянным Docker socket этим механизмом не запускается. Образы сверяются по точным ID, Python/npm lock-файлы — с фактическими файлами внутри локальных образов. Проверочные контейнеры одноразовые, без сети, capabilities и записи в корень.

## Подготовка издателем

Команды выполняются из корня проекта Python 3.11+ с `cryptography==50.0.1` (зависимость есть в `backend/requirements.lock` и `scripts/requirements-tls.txt`). В PowerShell с активной `.venv` используется `python`; без активации — `.\.venv\Scripts\python.exe`. Зависимости устанавливают на этапе подготовки поставки, до отключения сети.

Создать ключ издателя один раз:

```text
python scripts/software_package.py keys --directory .release-signing
```

Каталог должен быть новым. На Windows наследование ACL отключается, доступ даётся текущему пользователю; при отказе ACL ключи не записываются. На Linux каталог создаётся с 0700, закрытый ключ — с 0600. `publisher.key` остаётся у издателя; `publisher.pub` и его напечатанный SHA-256 передаются администратору отдельно. Каталог исключён из сборки, снимков программы и Git. Повторный запуск не заменяет имеющийся ключ.

Собрать необходимые образы, зафиксировать их ID, создать пакет:

```text
docker compose build
python scripts/software_package.py images --output artifacts/release-images.json
python scripts/software_package.py build --signing-key .release-signing/publisher.key --images artifacts/release-images.json --version 1.0.0 --description "Описание изменений выпуска" --output artifacts/release-1.0.0.zip
```

Сборка не читает содержимое рабочих данных/секретов. Она проверяет исходники до и после копирования и повторно проверяет готовый архив перед публикацией. Существующий файл выпуска не перезаписывается. Перед финальной сборкой обновляют перечни лицензий и выполняют `make check`; при смене зависимостей комплект образов собирают заново. Для Python-инвентаря нового образа без перезапуска приложения: `python scripts/build_libraries.py --python-only --python-image dispatcher112-backend`.

## Проверка администратором

```text
python scripts/software_package.py verify --package artifacts/release-1.0.0.zip --trust-key .release-signing/publisher.pub
python scripts/software_package.py prepare --package artifacts/release-1.0.0.zip --trust-key .release-signing/publisher.pub --target .updates/release-1.0.0
```

На целевой машине вместо `.release-signing/publisher.pub` указывают путь к заранее доверенному открытому ключу; закрытый ключ издателя там не требуется. `verify` проверяет все байты без распаковки и без Docker. `prepare` проверяет свободное место, наличие локальных образов и соответствие их зависимостей; сохраняет подписанный архив, проверенный каталог `program` и `state.json` со статусом `VERIFIED`. Каталог назначения ограничен `.updates` и должен быть новым. Ошибка не публикует частично подготовленный выпуск и не меняет работающие сервисы/данные. Подготовка не выполняет код из архива.

Сверка конкретной установленной версии или подготовленного каталога:

```text
python scripts/software_package.py integrity --package artifacts/release-1.0.0.zip --trust-key .release-signing/publisher.pub --root .
python scripts/software_package.py integrity --package .updates/release-1.0.0/release.zip --trust-key .release-signing/publisher.pub --root .updates/release-1.0.0/program
```

Результат содержит `passed`, отсутствующие, изменённые и лишние файлы; ошибка проверки или несовпадение дают код возврата 1. Нельзя использовать пакет другой версии для заключения о повреждении текущей установки. Сверка проверяет файлы программы относительно доверенного выпуска; она не является проверкой содержимого работающих контейнеров, пользовательских данных или уже применённых миграций.

## Оставшаяся часть этапа

Внутренние механизмы установщика реализованы отдельно: `update_files.py` сохраняет предыдущие файлы и подписанный ключом установки журнал, заменяет только программные пути, возобновляет прерванную замену/откат и проверяет результат. `.env`, `.secrets` и `data` не заменяются. Проверка идемпотентного повтора также обнаруживает лишний код. Прерванную операцию проверяли исключением между записями файлов; испытание физического отказа накопителя этим не заменяется.

`update_database.py` хранит операцию в `system_settings.software_update`, проверяет активного ADMIN, отсутствие занятия/генерации/звонка и исключительное владение обслуживанием. Этапы `STARTED → BACKED_UP → MIGRATED → READY → ACTIVE` требуют сведений о копии, ревизии и проверке сервисов. До активации допустим переход в `ROLLING_BACK → ROLLED_BACK`; `FAILED` сохраняет обслуживание. Повторы не дублируют аудит, а завершение возвращает исходное состояние обслуживания. Поле `maintenance.update_id` запрещает снять обслуживание или запустить параллельную техническую операцию через REST.

Перед возвратом БД установщик должен остановить все процессы записи и экспортировать новый аудит. Экспорт подписан ключом установки; импорт проверяет подпись, идентификатор обновления и SHA-256 всего исходного журнала до начала операции. Существующие совпадающие строки пропускаются; конфликт ID или отсутствующий пользователь запрещает импорт до вставки. Новые строки сохраняют ID, автора, время, IP и содержимое; последовательность ID продвигается, защитный триггер остаётся включён. Перенос ограничен 100 000 новых строк / 64 МиБ; превышение останавливает процедуру, а не обрезает аудит. Самостоятельно вызывать эти внутренние функции вместо полного установщика не следует: они не останавливают Docker и не проверяют результат миграции за вызывающий процесс.

Нельзя заменять рабочую папку распакованным `program` вручную: это обходит резервирование, миграции, обслуживание и аудит. Пакетный импорт учебных материалов/сценариев — отдельное требование и не заменяется пакетами ПО.

## Установка с обслуживанием и откатом

`scripts/install_update.py` выполняется на компьютере установки пользователем с доступом к локальному Docker. `--actor` — UUID действующего ADMIN из БД. Это отдельное от входа через браузер установочное полномочие; скрипт не предоставляет удалённый Docker socket. Завершите занятия, генерации и звонки; запустите все сервисы выбранной установки. Нездоровый исходный экземпляр сначала исправляют.

```powershell
python scripts/install_update.py apply --installation "C:\Dispatcher112" --package artifacts/release-1.0.0.zip --trust-key publisher.pub --actor UUID_АДМИНИСТРАТОРА --reason "Плановое обновление учебной программы"
```

Для восстановленного экземпляра дополнительно указывают `--deployment .recovery/ИМЯ/compose.json` и его `workspace` в `--installation`. Установщик проверяет подпись, локальные образы и зависимости обеих версий, свободное место на файловых системах программы и Docker, сохраняет прежние файлы и закрепляет образы отдельными тегами. Порты, тома, секреты, пользовательские каталоги, прежние значения окружения и привилегии сохраняются. Повышение основной версии PostgreSQL требует отдельной миграции кластера и здесь отвергается.

После административной проверки в БД включается обслуживание, останавливаются процессы записи, создаётся и проверяется полный снимок. Затем заменяются программные файлы, выполняются миграции и запускаются сервисы с проверками готовности. Успешный `apply` возвращает `READY` и печатает каталог транзакции. Обслуживание остаётся включённым до `activate`:

```powershell
python scripts/install_update.py status --installation "C:\Dispatcher112" --target "C:\Dispatcher112\.updates\install-ID"
python scripts/install_update.py activate --installation "C:\Dispatcher112" --target "C:\Dispatcher112\.updates\install-ID"
```

`activate` повторно проверяет файлы и готовность, публикует закреплённую конфигурацию запуска и снимает только принадлежащее обновлению обслуживание. В новой программе `make` использует `scripts/compose.py`: он проверяет HMAC указателя `.updates/active.json` и SHA-256 конфигурации, поэтому перезапуск не выбирает случайно перемещённые теги образов. Для восстановленного экземпляра обновляется и переданный `compose.json`; изменение этого файла другим оператором останавливает публикацию. `.env` и пользовательские секреты установщик не заменяет.

При обычной ошибке `apply` выполняет откат автоматически и возвращает ненулевой код. После аварийного завершения процесса используйте тот же каталог транзакции:

```powershell
python scripts/install_update.py resume --installation "C:\Dispatcher112" --target "C:\Dispatcher112\.updates\install-ID"
python scripts/install_update.py rollback --installation "C:\Dispatcher112" --target "C:\Dispatcher112\.updates\install-ID"
```

Не запускайте `apply` повторно вместо продолжения. Одновременные установщики блокируются файловой блокировкой; активный одноразовый процесс Docker запрещает повтор до его завершения. Перед восстановлением БД сохраняется подписанный новый аудит. Неудачная БД переименовывается в `dispatcher_failed_ID` и остаётся для разбора; прежняя восстанавливается из проверенного снимка, новые записи аудита импортируются без изменения исходного префикса и без дубликатов, возвращаются права и прежняя программа. Каталог транзакции, теги `dispatcher112-update:*` и резервные копии нельзя удалять, пока они нужны для запуска или восстановления.

После `ACTIVE` возврат старого снимка этой командой запрещён: он потерял бы последующее обучение. Для уже работающей версии требуется новое совместимое обновление; восстановление на прежний снимок со всей последующей историей остаётся отдельным критерием этапа 15. Непомеченная посторонняя БД на месте прерванного восстановления не перезаписывается. Проверки `READY` — техническая готовность сервисов; предметную проверку новой версии выполняют до активации. Подписанный запрос из административного UI исполняется отдельной локальной командой, описанной ниже.

## Работа через экран администратора

Оператор установки сначала получает открытый ключ издателя по доверенному каналу, сверяет его отпечаток и сохраняет как `.secrets/software-publisher.pub`. Закрытый ключ издателя на сервер переносить не нужно. Для нового ключа запустите одноразовый `prepare_runtime`; он выдаёт только backend копию открытого ключа, исходный файл не меняет. Если исходный ключ удалён, следующий prepare_runtime удаляет и прежнюю подготовленную копию. Пока ключа нет, UI показывает причину и запрещает загрузку.

В «Обновления программы» выберите ZIP и нажмите «Загрузить и проверить пакет». Проверка подписи и всех файлов проходит на сервере; браузер не распаковывает и не выполняет архив. Учебные материалы и программы имеют разные каталоги и права HTTP-доступа. Для архива используется `/data/materials/.software-updates` внутри уже существующего записываемого тома: расширять привилегии контейнера и добавлять Docker socket не требуется. Каталог включается в обычные резервные копии данных. Ненужные архивы можно удалить, сохранив аудит.

Выберите проверенный пакет и укажите причину установки. Скачайте подписанный JSON-запрос и пакет для сервера. Команда показана в UI; например:

```powershell
python scripts/install_update.py execute-request --request software-update-UUID.json --package release-1.0.0.zip
```

Запускайте её из папки этой установки. Для отдельного восстановленного экземпляра используйте операторский скрипт с `--installation .recovery/ИМЯ/workspace --deployment .recovery/ИМЯ/compose.json`. Запрос не даёт право выбрать произвольного автора, каталог, ключ или команду: эти параметры берутся из проверенных данных и серверной конфигурации. Файл другой установки, изменённый пакет, заменённый издатель или истёкшие 24 часа дают отказ. Идентификатор запроса становится идентификатором обновления; повторное применение не создаёт независимую установку. Для прерванного процесса используйте прежний `--target` и resume/rollback, а не новую установку.

Во время остановки API экран сообщает о недоступности и предлагает повтор. После запуска история показывает фактический READY. Проверьте новую версию, выберите «Активировать проверенное обновление», укажите причину и скачайте новый подписанный запрос. Его исполняют той же командой execute-request, уже без --package. До активации аналогично доступен запрос на откат. Само создание или скачивание запроса ничего не устанавливает: это явно написано в UI. Веб-приложение не получает постоянного доступа к Docker и не имитирует исполнителя. Для заявленной ручной операции требуется локальный оператор; полностью автоматический пульт управления сервисами остаётся отдельным критерием этапа 15.

Привязка запроса к установке использует совместно ключ backup-control и JWT_SECRET. Это учитывает восстановление снимка: ключ резервирования копируется, ключ сессий пересоздаётся. После восстановления, смены ключа сессий или перехода со старого формата подписи подготовьте новый запрос. Секреты в JSON не включаются; установщик читает ключ сессий из проверенной активной конфигурации выбранной установки.
