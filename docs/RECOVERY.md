# Состав снимка и границы восстановления

Новые снимки используют подписанный формат `dispatcher-backup-2`. В дополнение к БД, данным и настройкам они сохраняют исходный код установленной программы. Формат `dispatcher-backup-1` по-прежнему читается и проверяется; исходников в нём нет. UI показывает это различие для каждой копии.

## Что сохраняется

| Область | Содержимое |
| --- | --- |
| `database` | Один `database.dump`, созданный `pg_dump --format=custom --no-owner` |
| `data` | Учебные данные, материалы, WAV, записи, модели и служебные файлы из каталога данных |
| `config` | `.env`, Compose, инфраструктурные настройки и сертификаты/ключи; ключ подписи архива исключён |
| `program` | API, миграции, серверные тесты, исходники UI, локальные шрифты/звуки, скрипты, документация, Dockerfile, Makefile, Python lock-файл и `package-lock.json`, конфигурация сборки и исходное ТЗ |

Список корней и обязательных файлов задан явно в `backend/app/operations/program_files.py`. В программную часть не попадают `node_modules`, виртуальное окружение, кэши, промежуточная сборка, журналы или дополнительные `.env` внутри исходников. Рабочая `.env` хранится только в закрытой области `config`. Символические ссылки и отсутствие обязательного файла запрещают публикацию копии. После копирования повторно проверяются состав и SHA-256 исходников: изменение кода в процессе приводит к ошибке вместо публикации смешанной версии.

Все области используют общее хранилище объектов по SHA-256; повторные копии одинакового кода не дублируют его. Подпись HMAC защищает описание, контрольные суммы — содержимое каждого файла. Обычный API получает только количество файлов программы и версию формата, без путей и содержимого. Старые и новые форматы могут совместно храниться при одном правиле retention.

## Что реально проверяет «Проверить восстановление»

Исполнитель проверяет подпись и каждый объект, извлекает все четыре области в отдельный временный каталог и восстанавливает SQL в новую БД из `template0`. Исходная БД, рабочие исходники и конфигурация не заменяются. Результат сохраняет `schema`, `program_files`, число пользователей, типов и записей аудита, наличие защитного триггера и SQL-роль проверки. Временный каталог и эта проверочная БД удаляются после проверки.

Команда `make verify-backup` создаёт новый снимок и запускает такую проверку. UI администратора позволяет отдельно проверить выбранную старую или новую копию. Для старого формата результат содержит `program_files: 0`; это не считается повреждением копии, но требует соответствующего комплекта программы при аварии.

Приёмка 26.09.2026: `backup-20260926T123241Z-1d327af3549b`, 590 файлов / 1 954 344 636 байт, в том числе 363 файла программы; проверка восстановила 512 пользователей, 1200 типов, 28 686 записей аудита и защитный триггер от роли `dispatcher_backup`. Рабочая БД сохранена. Артефакты — `program-backup-live.log`, `backup-live.json`; 35 компоновок UI с явными фикстурами двух форматов и 7 компоновок с настоящим API прошли без ошибок/переполнения. `make check`: 588 pytest и 42 Vitest.

## Восстановление отдельного экземпляра

`scripts/recover_snapshot.py` — одноразовый локальный установщик. Он создаёт отдельный проект `dispatcher_recovery_<id>` с собственными PostgreSQL, Redis, служебными томами и архивами. Рабочая установка не заменяется и не останавливается. Постоянный Docker socket ни одному контейнеру не выдаётся; команды Docker выполняются самим установщиком на хосте.

Нужны установленный Docker Compose с поддержкой `volume.subpath`, локальные образы программы, каталог `.backups` и отдельно сохранённый `.secrets/backup-signing.key`. Нужен снимок формата 2, содержащий модуль `recovery_database.py` и TLS-конфигурацию; более ранние снимки остаются доступны для проверки файлов/БД. Установщик использует исходники из снимка, проверяет совпадение Python/npm lock-файлов с установленными образами, закрепляет их локальные SHA-256 ID и запрещает загрузку образов из сети.

Выберите идентификатор в пульте резервирования, затем из корня установки выполните (замените идентификатор снимка):

```powershell
python scripts/recover_snapshot.py prepare --snapshot backup-YYYYMMDDTHHMMSSZ-xxxxxxxxxxxx --target .recovery/restored
```

Команда проверяет подпись и SHA-256 файлов, восстанавливает код/данные/настройки в новый каталог и том, SQL — в новую БД, затем повторно выдаёт ограниченные прикладные права. На хосте нужен запас места для небольших файлов и кода; тяжёлые `data/llm` остаются в отдельном томе Docker. Дополнительного скачивания моделей нет. Исходный каталог `.backups` подключается к извлечению только для чтения. Новый каталог не может перезаписать существующий и должен находиться внутри `.recovery` этой установки.

До создания каталога/тома проверяется место на файловых системах проекта и Docker. На диске Docker резервируется два объёма снимка для подготовки, при первом возвращении расписания — один; на диске проекта учитываются извлекаемые файлы без моделей и SQL-дампа. На каждой используемой файловой системе дополнительно остаётся 4 ГиБ; если они общие, расходы суммируются, а запас учитывается один раз. Это предварительная оценка, а не квота и не защита от заполнения диска другими процессами. Проверка поддерживает локальный Docker Desktop WSL2 на Windows и обычный Docker на Linux. Windows использует текущий `CustomWslDistroDir`, Linux — `DockerRootDir`; удалённый движок и недоступный каталог отклоняются до записи. Приоритет `DOCKER_CONTEXT` над `DOCKER_HOST` соответствует [Docker CLI](https://docs.docker.com/reference/cli/docker/).

Готовый экземпляр открывается на `https://localhost:15173`, API — на порту 18000, RTP использует отдельный loopback `127.0.0.2:10000–10199/udp`. Параметры `--ui-port`, `--api-port`, `--media-address` позволяют выбрать другие свободные локальные значения. TLS использует сертификаты из снимка; при переносе на другой адрес/истечении сертификатов требуется штатная локальная подготовка сертификатов.

Восстановленная БД сначала находится в обслуживании. Старые задания резервирования и сведения о них перемещаются в `data/recovery-history/<snapshot>` и не исполняются повторно. Незавершённые генерации и SIP-вызовы получают FAILED с аудитом. Расписание копирования выключено до активации. Уроки, карточки и их исходные временные отметки сохраняются; фоновая выдача/истечение остановлены на время обслуживания, после активации используются реальные серверные сроки.

**Ключ JWT создаётся заново**, поскольку новый Redis не содержит прежнего списка отозванных сессий. Все пользователи входят повторно; пароли и TOTP из снимка сохраняются. Служебные SIP-пароли пересоздаются из нового ключа. Исходная `.env` в архиве и рабочей установке не меняется. Ключ подписи резервных копий сохраняется отдельно для проверки прежних и создания новых архивов.

После проверки восстановленной системы активируйте её:

```powershell
python scripts/recover_snapshot.py activate --target .recovery/restored
```

Активация повторно проверяет готовность сервисов, записывает `SYSTEM_RECOVERY_ACTIVATED`, снимает обслуживание и возвращает сохранённое расписание. Расписание возвращается один раз, что отмечается в `state.json`; повтор команды не дублирует событие и не затирает последующие изменения расписания или обслуживания администратором. Обычная кнопка снятия обслуживания до этой операции возвращает 409 `RECOVERY_NOT_ACTIVATED`. Если техническая операция в исходном аудите уже завершена, подготовка восстановления сохраняет её результат и не добавляет ложное сообщение об ошибке.

Остановить и вновь запустить этот экземпляр с сохранением данных:

```powershell
python scripts/recover_snapshot.py stop --target .recovery/restored
python scripts/recover_snapshot.py start --target .recovery/restored
```

Для работы используйте эти команды: файл `compose.json` содержит подготовленные пути и подключения томов. Обычный `make up` внутри восстановленного каталога не использует эту конфигурацию. `.recovery` исключён из Git и Docker build context; там находятся закрытые конфигурационные файлы.

Удаление **только восстановленных контейнеров и томов с их данными** требует явного флага; принадлежность тома проверяется по метке проекта. Каталог с состоянием/журналами на хосте сохраняется:

```powershell
python scripts/recover_snapshot.py remove --target .recovery/restored --delete-data
```

Реальная приёмка установщика: `python scripts/check_recovery_live.py --target .recovery/restored` на подготовленном тестовом экземпляре с демонстрационными учётными записями. Она активирует именно этот экземпляр и создаёт в нём учебные записи; исходная установка используется для входа и чтения аудита.

Проверка включает резервирование самим восстановленным приложением и остановку/запуск с проверкой содержимого таблиц, аудита, записи SIP и действующей сессии. Отдельный повтор этой части на активном тестовом экземпляре: `python scripts/check_recovery_persistence.py --target .recovery/restored --call-id UUID_ПРОВЕРЕННОГО_ЗВОНКА`. Сценарий использует локальные демонстрационные учётные записи, временно меняет расписание через API и возвращает его вместе с выключением обслуживания.

## Что ещё нужно для аварийного переключения

Снимок не содержит образы Docker, установленные Python/npm/системные зависимости и браузер. Для работы без сети они должны быть подготовлены отдельно в локальном комплекте поставки. Файлы lock и Dockerfile фиксируют исходные инструкции сборки, но не заменяют архивы образов. Ключ `.secrets/backup-signing.key` хранится отдельно от копии; его потеря лишает возможности подтвердить подпись. Сохранённая закрытая конфигурация делает весь архив конфиденциальным.

27.09.2026 добавлены локальные команды переключения основного адреса и возврата: [RECOVERY-SWITCH.md](RECOVERY-SWITCH.md). Обе БД сохраняются; недостающие события аудита импортируются с исходным содержимым и контрольной суммой, без переписывания существующих строк. При полном отказе исходного хранилища события после точки копирования нельзя получить из более раннего снимка. Переключение, повтор команды, возврат и продолжение прерванного возврата проверены отдельно: artifacts/ui-review/full-tz-recovery.json.
