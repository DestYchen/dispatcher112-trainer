# Развёртывание в изолированном контуре

## Подготовка вне контура

1. Подготовьте зависимости `scripts/requirements-tls.txt`, выполните `python scripts/bootstrap.py`, `python scripts/prepare_tls.py --activate`, `make models`, затем `make up`, `make seed` и `make check`. Миграции применяются отдельным установочным сервисом до запуска API и workers.
2. Сохраните образы в архив: `docker image save -o dispatcher112-images.tar dispatcher112-backend dispatcher112-worker dispatcher112-frontend dispatcher112-languagetool dispatcher112-backup dispatcher112-telephony postgres:15 redis:7 nginx:1.28-alpine ollama/ollama:0.34.4`. Сверьте имена через `docker compose images`.
3. Перенесите весь проект с `data/classifier.xlsx`, `data/streets.csv`, `data/voices/`, `data/fonts/`, `data/llm/`, `frontend/public/` и конфигурацией контейнеров. `.tools/`, `.venv/`, `node_modules/` и исходная модель TTS для работы не нужны. Секретные `.env` и `.secrets` не включайте в общий установочный архив.
4. Заранее подготовьте wheel-пакеты из `scripts/requirements-tls.txt`; для локальной приёмки также нужны `scripts/requirements-acceptance.txt` и браузер Playwright. Установщик сертификатов и браузерные тесты не участвуют в работе сервера.

## Установка без доступа в интернет

```sh
docker image load -i dispatcher112-images.tar
python scripts/bootstrap.py
python scripts/prepare_tls.py --activate
docker compose up -d --wait --no-build --pull never
make migrate
make seed
docker compose run --rm backend python -m app.seeds.demo
```

Не запускайте `make up`/`make demo` в неподготовленном изолированном контуре: эти цели допускают сборку. Команды выше используют только перенесённые образы и файлы. Дождитесь готовности LanguageTool: его healthcheck действительно проверяет русский текст и прогревает словарь.

Проверьте `/healthz`, войдите администратором и откройте «Состояние системы». Выполните цикл карточки, доклад 2201 и PDF. Внешнее соединение на этом этапе отключено; локальная сеть между браузером и сервером необходима.

## Учебный класс

По умолчанию HTTPS-шлюз доступен только на сервере, через 127.0.0.1. Для класса добавьте имя/IP сервера в сертификаты (`prepare_tls.py --host ... --activate`), настройте опубликованные адреса Compose и `SIP_MEDIA_ADDRESS`, разрешите вход из подсети класса и укажите точный `TLS_CORS_ORIGINS` в `.env` (JSON-массив). На клиентские места установите только публичный CA. Secure-cookie уже включены TLS-конфигурацией; подробности в [TLS.md](TLS.md). Пример явных переменных Compose:

```yaml
services:
  backend:
    environment:
      CORS_ORIGINS: '["https://dispatcher.class.local"]'
      COOKIE_SECURE: 'true'
  worker:
    environment:
      CORS_ORIGINS: '["https://dispatcher.class.local"]'
      COOKIE_SECURE: 'true'
```

Для внешнего локального TLS-шлюза используйте опубликованный 127.0.0.1:5173. Он должен передавать WebSocket Upgrade и Host. Браузер обращается к API и WAV по относительным путям. PostgreSQL, Redis, LanguageTool и worker наружу не публикуются. Не запускайте несколько процессов uvicorn: комнаты WebSocket рассчитаны на один процесс.

Создайте личного администратора и участников, настройте при необходимости TOTP. После проверки нового администратора заблокируйте открытые демонстрационные аккаунты. Секреты доступны только оператору сервера в `.env`/переменных окружения; изменение JWT_SECRET завершает прежние сессии.

## Права рабочих процессов

Все 13 постоянных сервисов имеют read-only корень и no-new-privileges; у основных процессов CapEff=0. Backend, workers, Asterisk, frontend, LanguageTool, Ollama и три Nginx используют UID/GID 10001. API записывает только материалы, речь, замечания и запросы backup; worker не меняет `/data`; SIP-worker записывает своё состояние/речь, но читает записи разговоров. Ollama читает модель из `/models:ro`, служебные файлы создаёт в `/tmp`; загрузка моделей остаётся установочной операцией.

Nginx пишет PID и временные файлы в ограниченный tmpfs `/tmp`, конфигурация и ключи доступны только для чтения. Vite использует `/tmp/vite` и отдельный небольшой tmpfs для загрузки конфигурации; исходники и зависимости закрыты для записи. `make check/test/fmt` запускают отдельный `frontend_checks` без сети и сервисных ключей; форматирование получает рабочие исходники для записи только в этой одноразовой операции.

Asterisk читает фиксированные include-файлы из `/etc/asterisk`, создаёт ARI/RTP-конфигурацию и внутреннюю временную БД в `/run/asterisk`. Runtime, журналы, spool и cache ограничены tmpfs. Записи разговоров остаются в `data/telephony/recordings`, данные учётных записей — в прежнем каталоге телефонии; они переживают пересоздание контейнера.

PostgreSQL и Redis стартуют с ограниченным набором CHOWN/DAC_OVERRIDE/SETGID/SETUID (у PostgreSQL также FOWNER), подготавливают владельцев и переключаются на UID/GID 999. Сам сервер работает без capabilities. Проверены и существующие данные, и первая инициализация пустых БД: `python scripts/check_database_initialization.py` создаёт два контейнера без сети с данными только в tmpfs, дожидается основного процесса и удаляет их после проверки.

Backup сохраняет UID 0 без capabilities: ему требуется читать оригинальные закрытые ключи и ранее созданные частные архивы. Исходные данные, настройки, секреты и скрипты смонтированы только для чтения; запись разрешена в `.backups`, очередь/состояние и отдельный том `backup_scratch` для временного восстановления. Группа 10001 обеспечивает чтение прикладных файлов и передачу подписанных результатов. Том scratch должен иметь свободное место для полного развёрнутого снимка; успешная проверка удаляет свой временный каталог. Это отдельный доверенный исполнитель, а не права веб-приложения.

SQL-подключение backup использует отдельную роль `dispatcher_backup` и `BACKUP_DB_PASSWORD`. В рабочей схеме ей выданы только USAGE и SELECT таблиц/последовательностей; запрещены изменение данных/аудита, DDL, создание ролей, чтение серверных файлов и переключение на прикладную роль. CREATEDB требуется для восстановления в собственную временную БД из `template0`; это право не ограничено префиксом имени на уровне PostgreSQL, случайное имя задаёт исполнитель. Миграция снимает явные членства в других ролях и лишние права, в том числе публичные права изменения таблиц/последовательностей. Если backup уже владеет рабочей БД или её объектами, выдача прав завершается ошибкой: права владельца нельзя отменить обычным REVOKE.

INHERIT оставлен для неявной роли `pg_database_owner`, чтобы владелец новой проверочной БД мог создавать объекты в её `public`; в рабочей БД backup владельцем не является. См. [роли PostgreSQL 15](https://www.postgresql.org/docs/15/predefined-roles.html) и [восстановление из template0](https://www.postgresql.org/docs/15/manage-ag-templatedbs.html). Это ограничение обычных SQL-операций, а не изоляция скомпрометированного исполнителя: для полного снимка backup по-прежнему читает закрытые `.env` и `.secrets`, включая установочные реквизиты. API этих файлов и архивов не получает.

При обновлении существующей установки выполните `make bootstrap`: недостающий BACKUP_DB_PASSWORD создаётся без изменения прежних секретов. На свободном стенде включите обслуживание, остановите только backup, выполните `make migrate`, затем `docker compose up --build --detach --no-deps --wait backup` и снимите обслуживание. Для смены BACKUP_DB_PASSWORD используйте тот же порядок после изменения значения в закрытой `.env`; одного `restart` недостаточно для замены окружения контейнера. Роль и права накладываются после каждой миграции, чтобы новые таблицы попадали в резервную копию.

Перед запуском `prepare_runtime` подготавливает владельцев только необходимых каталогов данных и частные копии сертификатов в восьми томах. Этот установочный контейнер использует UID 0, не имеет сети и Docker socket и завершается до старта зависимых сервисов. Исходные закрытые ключи сохраняют прежние права. Повторная подготовка сохраняет содержимое существующих материалов, записей и `feedback.jsonl`; ссылки в подготавливаемых путях отклоняются. `bootstrap.py` заранее создаёт каталоги и файл замечаний, чтобы Docker не создавал каталог вместо отсутствующего файла. После изменения Compose применяйте `up` с пересозданием изменённых контейнеров: `start` сохраняет старые монтирования.

Подписанные файлы обмена backup имеют режим 0640 и группу каталога. Группа выставляется явно: Docker Desktop на Windows не сохраняет setgid у bind-mount каталогов. API читает каталог и результаты, записывает только запросы; архивы ему не предоставляются. Восемь тестов проверяют подготовку/сохранность данных и границы доступа, `python scripts/check_runtime_permissions.py` проверяет действующие процессы и попытки записи. Подготовку приёмочных данных, требующую записи в корень `/data`, выполняйте через `docker compose run --rm checks python -m tests.ИМЯ_СКРИПТА`.

`scripts/check_runtime_permissions.py` проверяет UID, отсутствие capabilities, no-new-privileges, режим корня и реальные разрешённые/запрещённые записи у всех 13 сервисов. Установочные контейнеры `prepare_runtime`, `migrate`, `checks`, `frontend_checks` не считаются постоянными сервисами. Не переносите их права в работающий API. Техническая приёмка этапа 15 завершена; действующие результаты — PROGRESS.md. Постоянный контроллер выключен, подписанные операции выполняются локальной командой.

## Резервные копии и восстановление

Начиная с формата `dispatcher-backup-2` снимок также сохраняет исходники API/UI, миграции, тесты, локальные ресурсы, скрипты, документацию и файлы сборки/зависимостей. Проверка восстанавливает и эту область; старый формат остаётся читаемым, UI отмечает отсутствие исходников. Образы Docker и установочные пакеты нужны отдельно. Точный состав и границы аварийного восстановления — [RECOVERY.md](RECOVERY.md).

Для развёртывания отдельного работающего экземпляра используйте `python scripts/recover_snapshot.py prepare --snapshot ИМЯ_КОПИИ --target .recovery/restored`, затем после проверки `python scripts/recover_snapshot.py activate --target .recovery/restored`. Нужны формат 2 с протоколом восстановления, локальные совместимые образы и отдельно сохранённый ключ подписи. Установщик проверяет место на дисках проекта и Docker, сохраняет исходную установку и запускает новую на `https://localhost:15173`; все пользователи входят заново. Останавливать и запускать её следует действиями `stop`/`start` того же установщика, а не обычным `make up` внутри архива. Подробности, ограничения переключения основного адреса и реальная приёмка — [RECOVERY.md](RECOVERY.md).

Резервирование создаёт полный снимок: `pg_dump --format=custom`, данные, материалы, WAV, модели, `.env`, инфраструктурные настройки и сертификаты. Новый образ собран и запущен 26.09.2026; первый полный снимок из 156 файлов (1 946 593 357 байт) восстановлен в отдельный каталог и проверочную БД: 470 пользователей, 1200 типов, 28 332 записи аудита и его защитный триггер. Рабочая БД не менялась. Последняя проверка — `artifacts/ui-review/full-backup-verification.json`. Закрытый каталог — `.backups/`; хранятся 14 снимков в `snapshots`, общие файлы по SHA-256 — в `objects`. Приложению монтируется только общая папка данных, где `backup-status/manifest.json` содержит дату и идентификатор последней копии; полных копий в ней больше нет. Незавершённые `.partial` не считаются копиями. Запуск по расписанию после 03:00 Europe/Moscow, при неудаче повтор каждые 15 минут до успешного снимка за текущий день.

`make backup` создаёт копию сразу. Обновлённый `make verify-backup` создаёт один полный снимок, проверяет подпись/HMAC и контрольные суммы всех файлов, выгружает конфигурацию/данные во временный каталог и восстанавливает БД в `dispatcher_verify_<случайный идентификатор>`. После проверки данных и триггера аудита удаляется только эта проверочная БД; исходная БД не меняется. Правило 14 копий дополнительно покрыто тестом пятнадцати снимков с общими и различающимися файлами. Старые dump новой процедурой не удаляются.

Те же действия доступны администратору в «Резервных копиях» после включения обслуживания. Там же настраиваются ежедневное время по Москве, включение расписания и хранение 14–90 успешных копий; уменьшение числа применяется после следующей успешной копии. Расписание выполняет процесс backup, заменивший прежний cron; он проверяет наступление времени каждые 30 секунд, при ошибке повторяет через 15 минут. Результат каждой проверки сохраняется отдельно с подписью в `.backups/verifications/`; `verification.json` оставлен как совместимый указатель последней CLI-проверки. Интерфейс показывает только подписанную сохранённую историю.

Запросы и результаты лежат в `data/backup-operations/`, каталог и признак готовности — в `data/backup-status/`. Они подписаны отдельным ключом `.secrets/backup-control/token`; исходные копии в эти каталоги не попадают. Процесс выполняет только создание, проверочное восстановление и изменение расписания; Docker socket ему не предоставляется. Повторный идентификатор не запускает законченное действие заново. Перезапуск помечает незавершённую операцию ошибкой; фоновый монитор API записывает итог в аудит, даже если вкладка уже закрыта.

Копии содержат учебные персональные данные, хеши паролей и закрытые сервисные ключи. Каталог и `.secrets` должны быть доступны только оператору сервера. Ключ `.secrets/backup-signing.key` намеренно исключён из самого снимка: сохраните его отдельно на защищённом локальном носителе, иначе после потери сервера нельзя проверить подпись копии. Шрифты и исходный код остаются в комплекте программы.

**Старый dump** можно проверить в отдельной новой БД через контейнер backup: `createdb --template=template0 dispatcher_recovered`, затем `pg_restore --exit-on-error --no-owner --dbname dispatcher_recovered /backups/ИМЯ.dump`. Имя должно быть свободным; существующую БД не удаляйте. Эта БД принадлежит проверочной роли и не готова к переключению рабочего приложения: установочная процедура должна отдельно восстановить владельцев и прикладные права. Простая смена POSTGRES_DB теперь намеренно остановится на проверке владельца. Переключение основного адреса и возврат проверены; порядок — RECOVERY-SWITCH.md. Проверочное восстановление через UI выполняет отдельную проверку копии. Alembic `make migrate` применяет только недостающие миграции.

Журнал аудита хранится бессрочно; его триггер запрещает редактирование и удаление. Retention 14 относится к архивам БД, а не к строкам журнала. Контроль объёма и внешняя копия каталога backup выполняются средствами локальной инфраструктуры.

## Диагностика

Постоянные сервисы используют `restart: unless-stopped`: аварийное завершение процесса приводит к автоматическому запуску, ручная остановка сохраняется. Одноразовые `prepare_runtime`, `migrate` и `checks` автоматически не повторяются. Остановленный Docker Desktop необходимо запустить средствами Windows; политика контейнера не запускает сам Docker. Проверка `python scripts/check_process_recovery.py` выполняется на свободном стенде: включает обслуживание, завершает только процесс Vite, измеряет восстановление и снимает обслуживание. Артефакт `process-recovery.json`: 13 политик проверены, frontend восстановился за 4,032 с. Отказ отдельного узла относится к последующей кластерной приёмке.

`docker compose ps`, `docker compose logs backend worker languagetool`, `/admin/health`, `/metrics`. Сопоставляйте пользовательский X-Request-ID с JSON-логами. При отказе LanguageTool приложение продолжает работу, ось грамотности исключается с пометкой; при восстановлении новые оценки снова включают её. Уже сохранённые оценки не пересчитываются задним числом.

Оригинальные классификаторы и билеты заменяют учебные данные через импорт; форматы описаны в data/README.md. Исходные PDF заказчика отсутствовали при реализации, их OCR требует отдельной приёмки на самом корпусе.
