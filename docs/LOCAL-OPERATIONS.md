# Локальное техническое обслуживание

По умолчанию технический пульт использует локальные команды (`TECHNICAL_CONTROL_MODE=local`). Постоянный доступ контейнеров к Docker не нужен. Команды выполняют на компьютере установки из корня проекта; Python и Docker должны быть доступны этому оператору. В PowerShell с активной `.venv`:

```powershell
python scripts/technical_operations.py collect
```

Команда читает состояние, CPU, память и последние 100 строк журналов всех 13 рабочих сервисов текущего проекта. При установленном подписанном выпуске или офлайн-комплекте сравниваются реальные ID образов с закреплёнными ID, отдельно показан read-only корень. В обычном окружении разработки без закрепления показано отсутствие эталона образа. Это дополняет проверку файлов, не проверяя содержимое произвольных изменяемых томов. Значения секретных переменных скрываются до сохранения. Разовый снимок помечается устаревшим через пять минут.

## Автоматический мониторинг

`make up` и `python scripts/compose.py up --detach …` запускают один фоновый монитор; `make down` и `python scripts/compose.py down` останавливают его. На Windows окно не открывается. Монитор только читает Docker и передаёт подписанные измерения: он не исполняет ожидающие запросы UI, не открывает порт и не выдаёт контейнерам Docker socket. Сбор повторяется примерно раз в 10 секунд; при длительном сборе циклы не перекрываются. UI обновляется каждые пять секунд. Если новые измерения не приходят 30 секунд, состояние становится устаревшим, кнопки операций блокируются. Ошибка сбора не обновляет время старого успешного снимка.

Управление отдельно от сервисов проекта:

```powershell
python scripts/service_monitor.py start
python scripts/service_monitor.py status
python scripts/service_monitor.py stop
```

Остановка отзывается через файл владения в `.runtime`: чужие процессы по сохранённому PID не завершаются. Монитор заканчивает текущий цикл и выходит. В `.runtime/monitor-status.json` остаётся краткий результат последнего цикла без журналов или секретов; непрерывно растущего лог-файла нет. После полного отключения компьютера очередной штатный запуск проекта снова запустит монитор.

Для видимого сбора в текущем терминале: `python scripts/technical_operations.py watch --interval 10`; Ctrl+C останавливает только сбор. Допустимый интервал — 5–60 секунд. Устаревание для этого режима наступает после трёх интервалов.

## Выполнение операции из UI

1. Завершите занятия и включите обслуживание с причиной.
2. Выберите запуск/остановку/перезапуск сервиса либо лимиты CPU и памяти.
3. Скачайте запрос операции в папку проекта. Пока запрос не выполняется, его можно отменить в UI.
4. Выполните показанную команду, например:

```powershell
python scripts/technical_operations.py execute-request --request technical-operation-UUID.json
```

Подпись связывает запрос с установкой, пользователем, параметрами и сроком 24 часа. Исполнитель сверяет неизменяемый аудит и обслуживание до изменения контейнеров. Произвольные команды, пути, проекты и имена сервисов через UI не принимаются. Повтор завершённого запроса не перезапускает сервис снова. Результат и аудит обновляются автоматически; затем снимите обслуживание.

## Ресурсы и прерывание команды

Лимиты сохраняются в `data/materials/.technical-host/resource-limits.json`, входят в полную резервную копию и применяются оболочкой `scripts/compose.py`, в том числе при пакетном обновлении. Пользуйтесь `make up` / `python scripts/compose.py …`: прямой `docker compose` обходит эту настройку. Если Docker отказался применить ограничение, операция показывает ошибку; сохранённое желаемое значение остаётся для исправления и повторного применения.

Если процесс был прерван после начала операции, запрос не выполняется повторно автоматически. Проверьте фактическое состояние сервисов, восстановите backend при необходимости и завершите зависшую операцию как неуспешную:

```powershell
python scripts/technical_operations.py resolve-failed --job UUID
```

После этого можно создать новую операцию. Команда не откатывает и не удаляет данные. При недоступной БД/Redis сначала восстановите соответствующий сервис штатной командой Compose.

Для отдельно установленной восстановленной программы используйте `--installation ПУТЬ_К_WORKSPACE`. Её собственный подписанный deployment определяет проект; контейнеры основной программы не выбираются.

Проверены подписанные сервисные операции, сохраняемые лимиты, повтор запроса, монитор и восстановление/возврат. Серверные и установочные проверки включены в make check; фактические результаты — PROGRESS.md.
