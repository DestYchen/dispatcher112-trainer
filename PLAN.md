# PLAN.md — План реализации MVP-1

Порядок обязателен. Каждый этап заканчивается работающим состоянием, которое можно показать.

---

## Правила работы

1. **MUST** После каждого этапа — `make check` проходит целиком: линтеры, типы, тесты.
2. **MUST** Ни один этап не завершается с закомментированным кодом, `TODO` без номера задачи или заглушками, возвращающими фиктивные данные.
3. **MUST** Каждое бизнес-правило из `SPEC.md` покрыто тестом. Правило без теста считается нереализованным.
4. **MUST** Миграции только через Alembic. Ручной SQL в рантайме запрещён.
5. **MUST** Русские строки интерфейса — в `frontend/src/lib/strings.ts`, а не в разметке.

## Этап 3. Автомат статусов

Чистая логика, до всякого UI. **Это ядро продукта — делать тщательно.**

- `domain/enums.py` — `ResponseStatus`, `AssignmentState`, `ModifierCode`
- `domain/status_machine.py`:

```python
def available_transitions(current: ResponseStatus | None) -> list[ResponseStatus]: ...
def validate_transition(
    current: ResponseStatus | None,
    target: ResponseStatus,
    comment: str | None,
) -> None:  # поднимает InvalidTransition | CommentRequired
def is_terminal(status: ResponseStatus) -> bool: ...
```

**Приёмка — тесты обязательны на каждый пункт**

- Из `None` доступны ровно `ACCEPTED` и `NOT_ACCEPTED`
- Из `NOT_ACCEPTED` доступен ровно `ACCEPTED`
- Из `ACCEPTED` доступны пять статусов согласно таблице `SPEC.md` §4.2
- `WORK_COMPLETED` и `WORK_REFUSED` терминальны, из них недоступно ничего
- `NOT_ACCEPTED` без комментария → `CommentRequired`
- `NOT_ACCEPTED` с комментарием в 14 символов → `CommentRequired`
- `WORK_REFUSED` без комментария → `CommentRequired`
- Параметризованный тест: перебор **всех** пар (текущий, целевой), сверка с таблицей

## Этап 4. Занятие и выдача карточек

- `POST /teacher/lessons`, `/start`, `/finish`
- `realtime/clock.py` — планировщик с тиком 1 с, алгоритм из `SPEC.md` §5.3
- `realtime/hub.py` — WebSocket-хаб, комнаты по занятию и по роли
- `HEARTBEAT` каждые 5 с
- `GET /student/state`, `GET /student/assignments/{id}`
- Переход в `EXPIRED` по дедлайну

Сценарии на этом этапе создаются вручную через фикстуры — генерация в этапе 7.

**Приёмка**

- Тест: при `max_concurrent_cards = 3` четвёртая карточка не выдаётся, пока одна не закрыта
- Тест: карточка без первичного статуса через 31 с переходит в `EXPIRED`
- Тест: `card_interval_sec` соблюдается между выдачами
- Тест: первый `GET /student/assignments/{id}` ставит `opened_at` и создаёт `RECEIVED`; повторный — не меняет `opened_at`
- Вручную: два браузера, преподаватель запускает занятие → у студента появляется карточка < 2 с

## Этап 5. Рабочее место обучающегося

Полный UI по `UI.md` §4.

- Каркас, шапка с полосой «учебный режим»
- Очередь: сортировка по остатку, полоса дедлайна, подсветка новой, просроченные вниз
- Карточка: все блоки, вариант `EXTERNAL_SYSTEM`
- Панель действий: только `available_statuses` с сервера, обязательный комментарий, модальное подтверждение
- `POST /student/assignments/{id}/status`
- Таймеры от серверного времени, ресинхронизация по `HEARTBEAT`
- Звуки, регулятор громкости
- Горячие клавиши из `UI.md` §8
- Четыре состояния каждого представления, полоса потери соединения
- Локальная очередь действий при разрыве + `Idempotency-Key`

**Приёмка**

- Полный проход: карточка пришла → открыта → `ACCEPTED` → `RESPONSE_STARTED` → `WORK_COMPLETED` → закрыта
- Отказ без комментария невозможен: кнопка неактивна, сервер отклоняет прямой запрос
- Отключение сети на 20 с: таймер продолжает идти, действие уходит после восстановления, дубля нет
- Тест Playwright: полный путь карточки
- Тест Playwright: попытка невалидного перехода через прямой вызов API → `409`
- Контраст проверен: ни одна пара не ниже 4.5:1
- Навигация только с клавиатуры проходит весь цикл

## Этап 6. Движок оценки

- `scoring/engine.py` — четыре оси, веса из `lessons.settings`
- `scoring/rules/` — правило на файл, реестр нарушений с кодами, сообщениями и подсказками
- `scoring/rules/address.py` — сверка со справочником улиц, trigram-кандидаты
- `scoring/grammar.py` — клиент LanguageTool с таймаутом и деградацией: сервис недоступен → ось `literacy` исключается из расчёта, вес перераспределяется, в результат пишется пометка
- `POST /student/check-text` с debounce на фронте, оверлей подчёркиваний
- Расчёт при закрытии карточки и при завершении занятия
- Экран результатов студента

**Приёмка**

- Тест: одинаковый набор событий даёт одинаковый `total` при 100 прогонах
- Тест: реакция 24 с при дедлайне 30 с → `timeliness` = 100
- Тест: реакция 45 с → `timeliness` в диапазоне 40…100, строго меньше 100
- Тест: реакция 70 с → `timeliness` = 0
- Тест: отказ от профильного происшествия → нарушение `REFUSED_OWN_INCIDENT`, severity `CRITICAL`
- Тест: комментарий «не обслуживаем» без указания службы → `INCOMPLETE_COMMENT`
- Тест: «Дубининская» вместо «Дубнинская» → `ADDRESS_TYPO`, в `suggestions` есть верный вариант
- Тест: LanguageTool выключен → оценка считается, `literacy` помечен как пропущенный
- Каждое нарушение имеет непустые `message` и `hint` на русском

## Этап 7. Генерация сценариев

- `generation/builder.py` — пайплайн из `SPEC.md` §7.2
- `generation/llm.py` — `TemplateGenerator` и `LocalLLMGenerator` за общим протоколом

- Экран проверки эталонов, комментарий для перегенерации

**Приёмка**

- `GENERATION_BACKEND=template` работает без единой модели на чистой машине
- Генерация 40 сценариев завершается, процент отклонённых автовалидацией < 25 %
- Тест: сценарий с улицей вне справочника отклоняется
- Тест: сценарий, где описание противоречит модификатору, помечается на ручную правку
- Тест: `reference` вычисляется детерминированно — один и тот же тип даёт один и тот же эталон
- OCR билетов: распознано ≥ 90 билетов, ФИО и телефоны заменены на сгенерированные
- Отклонение с комментарием создаёт новую задачу, комментарий попадает в промпт

## Этап 8. Пульт преподавателя

- Таблица участников в реальном времени по WebSocket
- Агрегаты, частые ошибки группы
- Ручная выдача задания
- Режим наблюдения за экраном студента (только чтение)
- Завершение занятия с закрытием открытых карточек
- Переопределение оценки с записью в `audit_log`

**Приёмка**

- Действие студента отражается на пульте < 2 с
- Студент без действий 90 с при активных карточках → `alert: IDLE`, строка подсвечена
- Завершение занятия закрывает открытые карточки и запускает пересчёт
- Переопределение оценки не затирает `score`, видно обе величины
- Тест: пульт выдерживает 20 подключённых студентов, обновления не теряются

## Этап 11. Приёмка целиком

**Нагрузка**

- 20 одновременных сессий, по 10 карточек: p95 API < 300 мс, потерь WebSocket-сообщений нет
- Запись в БД ≥ 100 оп/с

**Безопасность**

- Прямые запросы к чужим `assignment_id` → `404`
- Студент не получает данные других студентов ни через один эндпойнт
- Секреты только из переменных окружения, в репозитории их нет

**Документация**

- `README.md`: требования, установка, запуск, сидирование, учётные записи по умолчанию
- `docs/ARCHITECTURE.md`: компоненты, потоки данных, схема БД
- `docs/DEPLOY.md`: развёртывание в изолированном контуре, чеклист офлайн-установки
- `docs/LIBRARIES.md`: полный перечень зависимостей с лицензиями — прямое требование ТЗ

**Демонстрация**

- Скрипт `make demo` поднимает систему с готовым занятием, тремя студентами и набором сценариев — для записи пятиминутного видео

## Порядок приоритетов, если время кончается

Резать с конца. Минимально защитимый продукт — этапы 0–6: полный цикл карточки с оценкой и результатами. Без этапов 7–10 решение всё ещё демонстрирует ядро задачи.

Ни при каких обстоятельствах не сокращать:

- Автомат статусов и запрет невалидных переходов
- Обязательные комментарии
- Оба таймера и серверное время как источник истины
- Проверку адресов
- Аудит действий

## Расширение по полному ТЗ заказчика от 01.09.2026

Запрос пользователя «доделай программу по ТЗ, плюс правки» расширяет границы исходного MVP. Этапы 0–11 выше сохраняют свою историю; перечисленные ниже этапы выполняются последовательно, с `make check` и записью в PROGRESS.md после каждого. Полная приёмка требует закрытия всей матрицы docs/CUSTOMER-SPEC-REVIEW.md, а не только интерфейса.

12. **Заполнение карточек.** Входящее учебное сообщение, отдельный режим занятия и смешанная выдача; серверные таймеры приёма/заполнения; черновик с защитой от перезаписи и offline; эталон скрыт до сдачи; детерминированная оценка полей, грамматики и адреса; преподаватель просматривает и преобразует сданную карточку в сценарий для действий. Проверки: полный браузерный цикл на широком/узком экране, сто одинаковых оценок, права, сроки, аудит, повторные запросы и восстановление черновика.
13. **Локальная IP-телефония.** SIP-сервер, программный телефон с гарнитурой, входящий и исходящий учебные вызовы без внешних маршрутов, предварительная подготовка реплик; реальное измерение медиазадержки ≤150 мс и 20 сессий.
14. **ИИ и история обучения.** Локальная подготовка сценариев моделью, воспроизводимый нейросетевой анализ и прогноз отдельно от регламентного балла; библиотека материалов, группы и назначенные модули, продольная история/обратная связь, настраиваемые критерии. Проверки реальных/прогнозных значений с разделением обучающих и контрольных данных, сохранённые версии моделей; синтетические метрики не выдаются за педагогическую валидность.
15. **Администрирование и безопасность.** Разделение преподавательских/технических прав, пульт сервисов/backup/пакетных обновлений, политики/конфигурация/мониторинг; TLS всех каналов, минимальные привилегии, восстановление и неизменяемый аудит.
16. **Масштабирование и приёмка.** Общая доставка событий нескольким узлам, отказ узла и восстановление, 100 пользователей с UI ≤2 с, ≥100 записей/с, отчёт <30 с, offline 30 с; проверки Chrome/Firefox/Яндекс и документирование непроверенных аппаратных платформ.
17. **Комплект поставки.** CSV/XML обмен и необходимые экспорты, презентация PDF/PPTX, сопроводительная документация DOCX/PDF, инструкции/лицензии/воспроизводимая сборка; предметная приёмка исходных классификаторов и PDF, ссылки для сдачи. Недоступные исходные данные или внешняя публикация фиксируются как конкретные остатки, без фиктивного выполнения.
